# Seam envelope (draft 0.1.0)

Stage: draft. This is not a release candidate, not ratified and not activated. Syafiq ratifies; nothing here ratifies itself. The namespace `com.syafiqkay.skills` is provisional until he confirms or replaces it. Entries marked **Proposed** are best guesses awaiting his confirmation (issue #109).

Sources: decision log C1, C6 to C9, P1 to P11 on #79, specification #90, ticket #91. sk-skills (SS) owns this public contract. sk-wiki (SW) owns meaning, policy, the binding and every private identifier.

## 1. Fields

Every operation report is one JSON object with exactly these keys. All are required.

| Field | Rule |
| --- | --- |
| `seam-version` | Seam version, `0.x.y`. Separate field. |
| `capability` | Capability name, for example `knowledge.ingest`. Separate field. |
| `capability-version` | Capability version, `0.x.y`. Separate field; moves independently of the seam version. A combined label such as `knowledge.ingest@0.1.0` is for human summaries only and is never a field value. |
| `run-reference` | Opaque, generated by SW per run, not derived from private content. Format in `tokens.md`. |
| `status` | `succeeded`, `partial`, `failed`, `refused`. |
| `disposition` | `reported`, `proposed`, `applied`, `skipped`. |
| `approval-state` | `not-required`, `pending`, `approved`, `denied`. |
| `error-category` | `invalid-request`, `not-permitted`, `conflict`, `backend-unavailable`, `internal`. Empty string when `status` is `succeeded`. **Proposed** (see section 8). |
| `grant-reference` | Opaque reference to the approved grant set for the run, or the reserved empty string when no grant applies. **Proposed** (section 8). |
| `counts` | Closed named integer keys (section 4). **Proposed** (section 8). |
| `mutation-summary` | Counts of requested, granted, applied, refused per operation class (section 3). |
| `extensions` | Object of namespaced extensions (section 6); `{}` when none. |

`refused` means the operation was not allowed to run. `failed` means it ran and broke. A `refused` report always carries `error-category: not-permitted`. A `failed` report carries a non-empty category. `partial` may carry either.

## 2. Closed vocabularies

The four vocabularies above are closed. A new value needs a new seam version, because a vocabulary change is a breaking change. Operation classes are also closed: `read`, `write-report`, `propose-change`, `apply-change`, `delete`.

## 3. Mutation summary

`mutation-summary` has one entry per operation class, each with four non-negative integers: `requested`, `granted`, `applied`, `refused`. Constraints: `applied <= granted <= requested` and `granted + refused <= requested`. It carries no targets and no content. SW decides what applies inside a grant; SS reports the counts.

A grant is a human-approved allowlist entry for one capability and one operation class. A mode, a role or a passing test grants nothing. A request outside a grant gives `status: refused` and `error-category: not-permitted`; it fails closed. Seam 0.1.0 defines no grant for `delete`, and `knowledge.ingest` 0.1.0 offers no `apply` mode. Deletion stays with Syafiq. The default conformance check enforces this. A separate, opt-in `--rc` draft check can accept approved mutation profiles (see `profiles.md`); it cannot verify that an approval is genuine, and the owner decides the allowlist.

## 4. Counts

**Proposed.** `counts` holds exactly six keys, each a non-negative integer: `seen`, `reported`, `proposed`, `applied`, `skipped`, `failed`. No other key is allowed. A new key is a breaking change. For `knowledge.ingest` 0.1.0, `applied` is always `0`.

## 5. Crossing rule

Default-deny. Only closed vocabulary values, SW-generated opaque references, counts and capability tokens cross the public seam. These never cross: checksums (not even as hashes), permalinks, identifiers, Drive identifiers, source and evidence content, query and answer content, approval records, mutation targets, before and after content, backend diagnostics. Anything else crosses only after Syafiq approves promoting it into this contract. The conformance check rejects envelope keys whose names suggest such data.

## 6. Extensions

- Key form `<namespace>.<name>`, with a reverse-DNS namespace owned by its definer. **Proposed:** the check requires at least two namespace labels plus a name (three or more dot-separated labels in all); each label is lowercase letters, digits and single hyphens, starts with a letter and does not end with a hyphen. Anything else is rejected with `invalid-request`. The SS namespace `com.syafiqkay.skills` is provisional.
- Unknown extensions are ignored, never an error.
- An extension may not add a vocabulary value, grant permission or change the meaning of a core field. **Proposed:** the check splits the whole key (namespace included) on `.` and `-` and rejects it with `not-permitted` when any token is a core word, or when the key contains one of the substrings `grant`, `permission`, `allow`, `vocab` (so `vocabulary`), `override`, `disposition` or `approval`. Core words: `mode`, `status`, `error`, `category`, `value`, `values`, `seam`, `version`, `capability`, `run`, `reference`, `count`, `counts`, `mutation`, `summary`, `extensions`, `state`, the operation-class words `read`, `write`, `report`, `propose`, `change`, `apply`, `delete`, and the count and summary keys `seen`, `reported`, `proposed`, `applied`, `skipped`, `failed`, `requested`, `granted`, `refused`. This is a deliberately conservative name filter, not a proof of intent.
- Extensions obey the crossing rule. **Proposed:** an extension value is a non-negative integer, a boolean or an opaque reference; free text and nested structures are rejected.

## 7. Versioning

The seam is versioned `0.x`. Any breaking change, including any vocabulary change, bumps the minor number. Capability versions move independently. A profile lists the seam versions it supports. Adding a capability does not change the seam version.

## 8. Proposed choices left open by #91

| Choice | Proposal | Why |
| --- | --- | --- |
| Grant reference placement | Required top-level `grant-reference`; reserved empty string when no grant applies. It names the approved grant set for the run, not one grant per class. | A fixed shape is easier to check than an optional field; one reference keeps the envelope small and the approval record private. |
| Counts shape | Closed named integer keys (section 4). | Free keys invite content leaks; a closed set can be checked mechanically. |
| Error category on `succeeded` | Empty string `""`. | Matches "empty" in #90; no null handling for consumers. |

The same proposed status applies to these tightenings, which do not add a value, field or permission to #90: the `refused`-implies-`not-permitted` pairing; a non-empty error category on `failed`; the arithmetic constraints in section 3; the reference formats in `tokens.md`; the mode-to-operation-class map in `profiles.md`; the extension value rule; and the extension key and name rules in section 6.

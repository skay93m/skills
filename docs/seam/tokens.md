# Token formats (proposal)

Status: **Proposed** for decision ticket #96. These formats need Syafiq's confirmation. Nothing here is final. SW-side generation is an SW decision.

All tokens are public, carry no private content and can be validated by pattern alone.

## Opaque references

| Token | Format | Rules |
| --- | --- | --- |
| Run reference | `run-` followed by 26 characters from `a-z2-7` | Generated by SW per run from a cryptographic random source (130 bits). Never derived from content, time, paths or identifiers. Never reused. |
| Grant reference | `grant-` followed by 26 characters from `a-z2-7` | Generated by SW when the approval is recorded; names a grant set. Never derived from the approval record. The reserved value `""` means no grant applies. |

Why random: a hash or sequence would let a reader test guesses or infer volume. Why a prefix: a consumer can tell a run reference from a grant reference and reject anything else.

## Capability token

**Proposed:** `<capability>:<operation-class>`, for example `knowledge.ingest:write-report`. It names exactly the scope of one grant (one capability, one operation class). The capability is lowercase dotted; the class is one of the five closed classes. The token is a label, not a secret, and grants nothing by itself. `knowledge.ingest:delete` is never valid in seam 0.1.0.

## Backend-constraint token

**SW input needed. Not final.** A backend-constraint token states a rule the backend promises to follow, such as a guard before a write. Proposal for the shape only: `bc-` followed by a kebab-case name of up to four words, drawn from a closed list that SW publishes per capability version, for example `bc-reread-before-write`. The profile field `backend-constraint-tokens` lists them; for `knowledge.ingest` 0.1.0 the list is empty until SW returns the list and meanings. The token names a promise only; the backend mapping stays private.

## Open questions for SW

1. Is the closed list of constraint names per capability version acceptable, or does SW need another shape?
2. How does SW generate references (random source, storage of the link to the private run record)?
3. Does SW want grant references per grant set (proposed) or per grant?
